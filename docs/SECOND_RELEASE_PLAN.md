# AgentNexus 第二次上线计划：多人稳定版

## 1. 上线目标

面向最多 10 名用户的内网或受控环境，完成从“单机试用版”到“多人稳定版”的升级。重点解决任务执行阻塞、任务状态丢失、用户数据隔离和运行故障难以定位的问题。

本次上线不追求高可用集群，也不引入 Kubernetes、复杂微服务或对象存储。数据库继续使用 SQLite，新增 Redis 和独立 Agent Worker。

## 2. 目标架构

```text
浏览器
  ↓
FastAPI API
  ├── SQLite：配置、任务、事件、记忆和产物元数据
  ├── Redis：任务队列、锁、实时事件和短期缓存
  └── 本地 data/：上传文件和生成文件
        ↓
     Agent Worker（1～2 个）
        ↓
模型、Skill、MCP、文件生成器
```

建议使用 Docker Compose 管理 `api`、`worker` 和 `redis`。开发环境仍保留 `start-local.sh`，允许不启动 Redis 时使用原有单机模式。

## 3. 范围和非目标

### 本次包含

- 基础登录和用户身份识别。
- 管理员与普通用户两级角色。
- 工作区、任务、附件和产物的服务端权限校验。
- Redis 任务队列。
- 独立 Agent Worker。
- 任务取消、重试、超时和失败恢复。
- SSE 事件在 API 与 Worker 之间的可靠转发。
- 基础审计日志、健康检查和备份说明。
- Docker Compose 多服务启动方式。

### 本次不包含

- PostgreSQL 或 MySQL 迁移。
- MinIO、S3 等对象存储。
- Kubernetes 和多节点高可用。
- 企业级 OIDC/LDAP 集成（预留扩展点即可）。
- 向量数据库和知识库重构。
- 任意代码沙箱或完整多租户平台。

## 4. 实施阶段

### 阶段一：基线、备份和运行契约

**目标：** 在改造前固定当前行为，保证随时可以回退。

**任务：**

1. 运行现有前端检查、Python 编译和回归测试。
2. 备份 `data/platform.db`、`data/uploads/` 和 `data/artifacts/`。
3. 记录任务、运行、事件和附件的现有状态字段。
4. 明确 API、Worker、Redis 的配置项和默认值。
5. 为任务状态、事件格式和队列消息建立版本号。

**交付物：**

- `docs/SECOND_RELEASE_PLAN.md`（本文件）。
- 数据库与运行数据备份脚本。
- 任务状态和事件格式说明。

**验收：** 备份可以恢复；现有单机启动和测试结果与改造前一致。

### 阶段二：身份认证和权限

**目标：** 允许 10 名用户安全共享系统。

**任务：**

1. 增加用户表、密码哈希、登录会话和登出接口。
2. 增加管理员、普通用户角色。
3. 从服务端会话获取 `user_id`，不信任客户端传入的身份字段。
4. 为工作区增加成员关系和访问级别。
5. 对任务、附件、产物、记忆、知识库和对话摘要增加权限过滤。
6. 管理模型、Skill、MCP、策略和用户的接口仅允许管理员访问。
7. 增加登录、配置变更、文件访问和任务控制的审计事件。

**建议接口：**

```text
POST /api/auth/login
POST /api/auth/logout
GET  /api/auth/me
GET  /api/users
POST /api/users
PUT  /api/users/{user_id}
```

**验收：** 用户 A 无法读取用户 B 的任务、附件和产物；无权限 API 返回 403；停用用户后会话失效。

### 阶段三：Redis 队列和 Worker

**目标：** API 不再直接承担长时间 Agent 执行。

**任务：**

1. 增加 Redis 配置、连接检查和启动失败提示。
2. 选择轻量队列库（推荐 Arq 或 RQ）。
3. API 创建任务后写入数据库并投递队列。
4. Worker 从队列读取 `task_id` 和 `run_id`，重新加载数据库状态后执行。
5. 使用 Redis 锁保证同一个 `run_id` 只有一个 Worker 执行。
6. 增加 Worker 心跳、租约和失联检测。
7. 支持 1～2 个 Worker 并行执行。
8. 保留无 Redis 时的本地开发降级模式，并明确提示该模式不适合多人使用。

**队列消息最小字段：**

```json
{
  "version": 1,
  "task_id": "...",
  "run_id": "...",
  "workspace_id": "...",
  "priority": 50,
  "attempt": 1
}
```

**验收：** API 请求在任务执行期间仍能正常响应；两个任务可以并行运行；Worker 重启后未完成任务可以恢复或进入可重试状态。

### 阶段四：任务控制和事件流

**目标：** 让任务的取消、重试、恢复和实时展示在多人环境中可靠工作。

**任务：**

1. 统一 `queued/running/waiting_approval/succeeded/failed/cancelled/retrying` 状态转换。
2. 增加任务超时和最大重试次数。
3. 取消操作写入数据库并通过 Redis 发送取消信号。
4. Worker 在模型调用、工具调用和文件生成之间检查取消状态。
5. Worker 将事件写入数据库，并通过 Redis 发布实时通知。
6. SSE 连接断开后按游标补发事件，避免重复展示。
7. 任务结束后保留事件历史，Redis 只承担实时转发。

**验收：** 取消任务不会继续产生新的工具调用；SSE 断线重连后事件顺序正确；重复投递不会生成重复产物。

### 阶段五：文件、模型和工具的运行边界

**目标：** 控制多人并发时的资源消耗和外部调用风险。

**任务：**

1. 为单任务设置最大执行时间、最大模型调用次数和最大工具调用次数。
2. 统一模型、MCP、HTTP 工具的超时和重试配置。
3. 限制单用户并发任务数，建议默认 2 个。
4. 限制上传文件大小、数量和单任务附件总量。
5. Worker 使用非 root 用户运行，并限制可访问目录。
6. 保留现有网络总开关、主机白名单和 stdio 命令白名单。
7. 高风险工具继续要求显式启用或人工审批。

**验收：** 超时任务自动终止；单个用户无法占满全部 Worker；工具和模型不会访问白名单外目标。

### 阶段六：Docker Compose 和部署切换

**目标：** 提供可重复的多人版启动、停止和升级流程。

**服务：**

```text
api       FastAPI HTTP/SSE 服务
worker    Agent 执行进程
redis     队列、锁和事件转发
```

**任务：**

1. 拆分 `api` 和 `worker` 镜像入口。
2. Redis 使用持久化卷。
3. SQLite 使用独立数据卷并定期备份。
4. 增加 `/api/health` 对 Redis 和 Worker 的状态检查。
5. 提供 `.env.release.example`，区分开发和多人版配置。
6. 编写启动、停止、升级、备份和恢复命令。
7. 默认只绑定内网或 `127.0.0.1`，不直接暴露公网。

**验收：** 一条 Compose 命令可以启动全部服务；停止并重新创建容器后任务和数据仍可用。

### 阶段七：测试、试运行和正式上线

**目标：** 在正式给 10 名用户使用前完成回归和故障演练。

**测试清单：**

- 登录、登出、停用用户。
- 用户和工作区权限隔离。
- 普通任务、专家任务和文件生成。
- 多任务并发执行。
- Worker 重启和 Redis 重启。
- API 重启和 SSE 断线重连。
- 任务取消、重试和恢复。
- 模型失败、MCP 超时和网络关闭。
- 上传文件越权访问和路径穿越。
- 数据库备份、恢复和版本升级。

**试运行建议：**

1. 先由 2 名用户试用 3～5 天。
2. 修复高频问题后扩展到 5 名用户。
3. 连续稳定运行至少 1 周后开放给全部 10 名用户。

## 5. 配置建议

```env
APP_DB_PATH=/app/data/platform.db
REDIS_URL=redis://redis:6379/0
APP_WORKER_COUNT=1
APP_MAX_CONCURRENT_TASKS_PER_USER=2
APP_TASK_TIMEOUT_SECONDS=1800
APP_TASK_MAX_RETRIES=2
APP_ALLOW_OUTBOUND_NETWORK=false
APP_ALLOW_STDIO_MCP=false
APP_ALLOW_REMOTE_MCP=false
APP_SECRET_KEY_FILE=/app/data/.secret_key
```

认证开关默认关闭，以保持本地开发兼容。初始化时可通过 `APP_ADMIN_USERNAME` 和 `APP_ADMIN_PASSWORD` 创建管理员；已经存在的账号不会被环境变量覆盖。用户、密码哈希和会话摘要保存在 SQLite。管理员登录后可以使用 `/api/users` 创建独立用户、重置密码或停用账号；普通用户无权访问这些管理接口。密码、角色或启用状态变更会撤销该账号的已有会话。

以上是认证及用户管理接口的当前实现说明，不表示多人上线已验收。工作区成员关系、资源所有权校验、登录页面及其管理界面仍须按本计划落实；环境变量中的共享普通账号不能替代独立用户。

生产或内网部署时应修改默认密钥，并把 Redis 和管理接口限制在内部网络。

## 6. 回滚方案

1. 保留当前单机启动路径和旧数据库备份。
2. 新版 Worker 出现问题时，停止 Worker，暂停新任务，使用单机模式处理紧急任务。
3. 回滚前导出未完成任务和事件记录。
4. 不直接覆盖 `data/`，先复制到带时间戳的备份目录。
5. 认证和数据库结构变更使用可逆迁移，禁止直接删除旧字段。

## 6.1 备份与恢复

服务停止或需要人工维护时，可以执行：

```bash
scripts/backup-data.sh --quiesced
scripts/restore-data.sh backups/agentnexus-时间戳-进程号 restore-staging/待验收
```

备份前应停止 API 和 Worker，`--quiesced` 表示操作者已确认停机。脚本使用 SQLite 备份接口，并包括默认数据目录中的附件、产物和 `.secret_key`，最后生成 SHA-256 清单。恢复会验证完整性且只写入不存在的新目录，不覆盖运行数据。目录切换、外部密钥和自定义路径限制见 `docs/BACKUP_RESTORE.md`。

## 7. 完成标准

满足以下条件后，才认为第二次上线完成：

- 10 名用户可以登录并按工作区使用系统。
- 用户无法越权读取任务、文件和产物。
- API 和 Worker 可以独立重启。
- 至少两个任务可以并行执行。
- 任务取消、重试、超时和恢复均有明确结果。
- SSE 断线后可以继续查看任务进度。
- Redis、SQLite 和 Worker 状态有健康检查。
- 数据库和文件有可验证的备份与恢复流程。
- 关键操作有审计记录。
- 前端检查、后端测试和故障演练通过。

## 8. 后续升级入口

第二次上线稳定后，再考虑第三次上线：

- SQLite 迁移 PostgreSQL。
- 本地文件迁移 MinIO/S3。
- 接入 OIDC/LDAP。
- Worker 容器隔离和资源配额。
- PostgreSQL + pgvector 知识库。
- Prometheus、Grafana 和 OpenTelemetry。
